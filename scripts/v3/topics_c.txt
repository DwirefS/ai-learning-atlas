f-gpu-hw|A GPU is many streaming multiprocessors (SMs) sharing an L2 cache and high-bandwidth memory (HBM). Tensor Cores do the matrix math, fastest in low-precision formats such as BF16, FP8 and FP4. HBM size limits what fits; HBM bandwidth limits decode speed. MIG splits one GPU into isolated slices; MPS lets processes share SMs concurrently. GPUs throttle when hot or power-capped, so clocks matter as much as utilization. Learn the failure modes too: ECC errors, fallen-off-the-bus events, and NVLink errors.
f-gpu-sw|The software stack goes kernel driver, CUDA (or ROCm) runtime, libraries such as cuDNN, cuBLAS and NCCL, then frameworks. The NVIDIA Container Toolkit exposes GPUs to containers. CUDA_VISIBLE_DEVICES controls which GPUs a process sees. The classic production bug is version skew: a container built for a newer CUDA than the node's driver supports, or different driver versions across nodes in one training job. Pin and inventory versions everywhere.
f-k8s-dev|Kubernetes sees GPUs through device plugins that advertise resources like nvidia.com/gpu. The NVIDIA GPU Operator installs and manages the driver, container toolkit, device plugin, DCGM exporter, MIG manager and feature discovery as one unit. Use ResourceQuotas to cap GPUs per namespace, and taints plus node affinity to keep non-GPU pods off expensive nodes. Dynamic Resource Allocation (DRA) is the newer API for richer device requests.
f-k8s-work|Training fits Jobs (or JobSet, Kubeflow Training Operator, or Ray via KubeRay); serving fits Deployments behind autoscalers. Model weights are large, so pull them with init containers or sidecars, or mount a shared volume or cache to avoid every pod downloading 100 GB. EmptyDir on local NVMe is fast scratch; PVCs persist. Apply pod security standards even to GPU workloads, and use PriorityClasses so production serving can preempt experiments.
f-linux-os|GPU nodes need care at the OS layer. Enable persistence mode so the driver stays loaded and first calls are not slow. NVSwitch systems require the Fabric Manager service, or multi-GPU jobs fail. Match driver and CUDA userspace per NVIDIA's compatibility matrix. IOMMU and PCIe ACS settings can silently cut peer-to-peer bandwidth. Run health checks (DCGM diagnostics) at boot and periodically to catch bad GPUs before jobs land on them.
f-linux-ct|Containers reach GPUs through runtime hooks (the NVIDIA Container Toolkit or CDI) that mount device files and driver libraries. Avoid privileged containers; mount only needed devices. Keep seccomp and AppArmor profiles on. Pin images by digest so a tag update cannot change your CUDA stack overnight. Scan images, since AI images are huge and pull in many dependencies.
f-sched-batch|Slurm still runs most HPC and many training clusters: partitions group nodes, GRES describes GPUs, and fairshare balances users. Gang scheduling starts all pods of a distributed job together or none at all, preventing deadlock where half a job holds GPUs waiting for the rest. Preemption reclaims GPUs for higher priority work, so jobs must checkpoint. Reservations hold capacity for planned runs.
f-sched-svc|Serving autoscalers should scale on queue depth, tokens per second, or KV usage, not CPU. Kueue adds job queueing, quotas and fair sharing across teams on Kubernetes; Volcano offers gang scheduling and batch policies. KubeRay manages Ray clusters for serving and training. Binpacking fills nodes tightly to free whole nodes; spreading improves resilience. Spot GPUs need graceful drain and fast restart.
f-store-types|Object storage (S3 and equivalents) holds checkpoints and datasets cheaply but with high latency. Parallel file systems (Lustre, GPFS, WEKA, VAST) feed training at high throughput. Local NVMe gives the fastest scratch and model cache. Container and model registries store versioned artifacts. Vector indexes have their own storage needs, mostly RAM and SSD.
f-store-pat|Store models and datasets as immutable, versioned artifacts with hashes. Speed up cold starts with peer-to-peer distribution, lazy-loading image formats, or node-local caches. Stream datasets instead of copying them to every node. Back up checkpoints across regions. Plan bandwidth: 100 nodes each pulling a 140 GB model at once is 14 TB of traffic.
f-net-fab|Inside a server, NVLink and NVSwitch connect GPUs at hundreds of GB/s, far above PCIe. Between servers, InfiniBand gives low latency and lossless transport; RoCE runs RDMA over Ethernet but needs careful congestion control (PFC and ECN). New AI Ethernet NICs and switches aim to match InfiniBand. PCIe topology matters: a GPU and NIC on different CPU sockets cross a slow link.
f-net-lib|NCCL picks algorithms and transports automatically, but environment variables such as NCCL_DEBUG=INFO, NCCL_SOCKET_IFNAME and NCCL_IB_HCA reveal and control its choices. GPUDirect RDMA lets NICs read GPU memory directly, skipping the CPU. Topology-aware placement keeps communicating ranks close. Packet loss shows up as slow or hung collectives, not errors. Monitor link counters and run nccl-tests regularly.
f-proc-buy|GPUs come through on-demand cloud, reservations and committed-use discounts, spot instances, newer GPU clouds, or owned hardware. Reservations trade flexibility for price and availability guarantees. Spot is cheap but can disappear at any moment. Owned hardware has the lowest unit cost at high utilization, but lead times for GPUs, power and data center space can run many months.
f-proc-fit|Pick hardware for the workload. Large models need enough HBM per GPU or per NVLink domain. Training and tensor-parallel serving need high-bandwidth interconnect SKUs. Check power and cooling: modern racks can exceed 100 kW and need liquid cooling. Confirm your software stack supports the accelerator. Consider lock-in to one vendor's ecosystem when committing for years.
f-obs-met|DCGM exposes GPU metrics: SM activity, memory bandwidth, temperature, power, ECC and XID errors. Engine metrics (vLLM, SGLang, TensorRT-LLM) cover queue depth, KV usage, TTFT and token rates. Add AI API SLIs per route. Track power and estimated carbon. Join metrics with cost so dashboards show dollars per million tokens, not just utilization.
f-obs-ops|Write runbooks for common incidents: GPU fell off the bus, NCCL hang, OOM loops, KV thrash, provider outage. Use error budgets to balance velocity and stability. Know the incident archetypes so on-call recognizes them quickly. Run blameless postmortems. Page on quality regressions as well as availability, since a model that answers wrongly at full speed is still an outage.
f-sec-iso|Isolation for GPU workloads uses namespaces and network policies, MIG for hardware-partitioned GPUs, and sandbox runtimes such as gVisor or Kata Containers for untrusted code. Control egress tightly so a compromised workload cannot exfiltrate weights or data. Confidential computing on recent GPUs encrypts memory and attests the environment, protecting data even from the host operator.
f-sec-sup|Sign container images and model artifacts, and keep SBOMs. Record model provenance: where weights came from and their hashes. Prefer safetensors over pickle-based formats, which can execute code on load. Admission controllers block unsigned or unscanned images. Store secrets in a vault, never in images or env files baked into models. Set SLAs for patching vulnerabilities.
f-cloud-svc|Clouds offer managed model APIs, managed Kubernetes with GPU node pools, spot GPUs, marketplace models, and serverless GPU platforms that scale to zero. Managed services cut operational load; raw GPU instances give control and often better unit cost at scale. Most organizations use a mix.
f-cloud-ops|GPU quotas are scarce and approved per region, so request them well ahead. Use private networking to reach model endpoints without the public internet. Set up cross-account roles so teams share capacity safely. Alert on cost anomalies daily, since a forgotten 8-GPU node costs thousands per week. Build GPU workloads into your landing zone with guardrails from the start.
f-en-fac|AI racks draw 40 to 130+ kW versus under 10 kW for classic servers. Air cooling tops out around 30 to 40 kW per rack; beyond that you need rear-door heat exchangers or direct liquid cooling. PUE (facility power divided by IT power) measures overhead. Utility power can take years to provision, which now gates AI expansion more than GPU supply. Plan redundancy for power and cooling, not just servers.
f-en-ops|Measure energy per million tokens so efficiency improvements are visible. Carbon-aware scheduling moves flexible batch work to times or regions with cleaner power. Reporting rules increasingly require energy and emissions disclosure. Thermal incidents (cooling failures) can throttle or shut down racks within minutes, so monitor and alert on inlet temperatures. Efficiency gains from quantization and better batching directly cut power.
f-train-soft|Large-scale training combines several kinds of parallelism. FSDP and ZeRO shard parameters, gradients and optimizer states across data-parallel ranks. Megatron-style tensor and pipeline parallelism split the model itself. Checkpoints must be sharded and written asynchronously to avoid stalling. Mixed precision (BF16, FP8) speeds training. Profile regularly to find communication bottlenecks.
f-train-ops|Big jobs fail often, so design for it. Elastic training continues when nodes drop. Preemption needs fast checkpoint and restart. Map ranks to topology so heavy communication stays on fast links. Fairshare policies balance teams. Run failure drills: kill a node mid-run and confirm the job recovers within your target time.
f-mlops-exp|Track every run with code version, data version, hyperparameters and metrics (MLflow, Weights & Biases and similar). Version datasets so results are reproducible. For LLM apps, track prompt lineage as carefully as code. Pin environments with containers or lock files. Store artifacts in a registry with metadata so anyone can find the model behind a deployment.
f-mlops-cd|Deliver models like software: CI runs evals, CD promotes artifacts through stages with canaries or shadow traffic. Feature flags let you switch prompts or models without redeploying. Keep rollback one click away. Record who approved what and when, because regulators and incident reviews both ask.
f-edge-des|Edge and sovereign sites range from a single appliance to a full cluster. Air-gapped sites need offline registries for images and models, local DNS and PKI, and a hardware root of trust. Measured boot and signed software let you prove what is running. Design for operation with no internet at all.
f-edge-ops|Remote attestation verifies that a site runs approved software. Break-glass procedures handle emergencies with logged access. Telemetry must reveal health without leaking data. Plan for field-replaceable units and spares, since a failed GPU in a remote site cannot wait for a cloud ticket. Support staff may need clearances.
f-fin-alloc|Allocate GPU cost to teams with showback or chargeback using labels and quotas. Idle killers reclaim notebooks and dev pods left running. Binpacking packs work onto fewer nodes so others can scale down. Carbon-aware placement can be part of allocation policy. Quotas have economic meaning: they are budgets in GPU-hours.
f-fin-gov|Set budgets per team and alert before they are hit. Detect anomalies such as sudden throughput drops (wasted GPUs) or token spikes. Report to executives in unit terms: cost per million tokens, cost per training run, utilization. Design incentives so teams benefit from efficiency. Rightsize regularly, since models and traffic change.
g-mental-loop|An agent is a loop: perceive the current state, reason about what to do, act with a tool, observe the result, and repeat. Keep explicit state (task, plan, facts learned) separate from the raw transcript, which grows and gets noisy. Define stop conditions: success, failure, or budget exhausted. Budget steps, tokens and dollars. Log every step so you can debug and evaluate later.
g-mental-when|Scope discipline saves projects. Start with a fixed workflow. Move to a single agent with tools only where decisions genuinely depend on intermediate results. Use multi-agent systems last, for parallelism or very different contexts. Put human checkpoints before risky steps and keep a kill switch that stops all agent activity immediately.
g-tools-des|Tools are the agent's API surface, so design them like a product. Make them task-oriented with strict schemas and enums. Mark side-effect classes (read, write, irreversible) so the harness can apply the right policy. Return structured errors the model can understand and fix. Make writes idempotent so retries after crashes are safe.
g-tools-disc|Agents choose tools from descriptions, so write descriptions as instructions with examples. With dozens of tools, load them dynamically per task to avoid confusing the model and wasting context. Capability tokens grant scoped, time-limited permissions per tool. Version tools and deprecate carefully, since prompts and trained behavior may depend on old names.
g-harness-parts|The harness is everything around the model. The loop driver runs turns. Middleware applies policy, logging, redaction and approvals in a fixed order. Compaction summarizes context when it grows. Checkpoint and resume let long runs survive crashes. Trace export feeds debugging, evals and training. The same model can perform very differently in two harnesses.
g-harness-fail|Common harness failures: infinite loops when the model repeats a failing call; context blowups from giant tool outputs; silent tool failures that return empty results the model treats as truth; prompt injection arriving through tool results; and retries that repeat non-idempotent actions. Each has a harness-level fix, not a prompt fix.
g-harness-rel|Reliability features: per-tool timeouts; idempotency keys on every side effect; crash recovery from checkpoints; deterministic replay of recorded tool responses for debugging; and a carefully chosen middleware order (for example, redact before logging, authorize before executing).
g-harness-ctx|Context control keeps long runs coherent. Compaction strategies include summarizing old turns, dropping stale tool payloads, and keeping hierarchical summaries. Pin critical spans such as the task goal and user constraints so compaction never removes them. Budget tokens per section so tool output cannot crowd out instructions.
g-mem-types|Agent memory comes in types. Working memory is the current context. Episodic memory stores past trajectories. Semantic memory holds facts, usually in a vector store. Procedural memory captures skills or reusable instructions. Most useful systems combine a few of these with explicit rules about when to read and write each.
g-mem-ops|Memory needs policies. Decide what is worth writing; saving everything creates noise. Summaries lose detail, so keep links to sources. Retrieval can surface irrelevant or outdated memories. Support deletion for privacy. Evaluate memory by whether it improves task success, not by how much it stores.
g-mcp-arch|The Model Context Protocol connects AI hosts to external capabilities. A host application runs MCP clients, each talking to one MCP server. Servers expose tools (actions), resources (readable data) and prompts (templates). Transports include stdio for local servers and streamable HTTP for remote ones. Gateways sit in front of many servers to centralize auth, policy and logging.
g-mcp-sec|MCP servers are code with access to your systems, so treat them as supply chain. Use OAuth with scoped, short-lived tokens. Pin server versions and tool manifests so a server cannot silently change a tool's description or behavior (a "rug pull"). Restrict egress. Enforce policy at a gateway. Review third-party servers before installing, exactly as you would a library.
g-a2a-concepts|Agent-to-agent (A2A) protocols let independent agents delegate tasks to each other. Unlike calling a tool, delegation hands off a goal to an autonomous peer. Agents advertise capabilities in agent cards for discovery. Tasks have a lifecycle (submitted, working, input-required, completed, failed) with streaming updates. Each agent authenticates and authorizes the others, and failures must be contained so one bad agent does not cascade.
g-a2a-ops|Operating multi-agent systems needs contracts: what each agent promises, with SLAs. Trace requests across agents with shared trace ids. Version agent interfaces. Consider abuse: a compromised agent can send malicious tasks. And often the right answer is a single agent with tools, which is simpler to debug and secure.
g-multi-topo|Supervisor-worker is the common production topology: one coordinator splits work and merges results. Pipelines chain specialists in fixed order. Debate or critic setups have agents review each other. Hierarchies nest supervisors for large tasks. Market-style bidding exists in research but is rare in production.
g-multi-coord|Agents coordinate through shared state (a database, files, or MCP resources) or through A2A delegation. Handoffs need clear protocols: what context passes and who owns the task. Contain failures so one stuck agent does not block others. Attribute cost per agent and per task, because multi-agent runs can quietly multiply token spend.
g-sec-iso|Run agent code and browsing in isolation: OS sandboxes (seccomp, namespaces), microVMs such as Firecracker, and remote browser isolation. Give each task an ephemeral filesystem that is destroyed afterward. Apply network policy with egress allowlists so a hijacked agent cannot reach arbitrary hosts or internal services.
g-sec-pol|Policy limits what an agent may do. Require human approval for writes and anything irreversible. Set rate and spend limits. Use classifiers to flag sensitive actions. Apply injection defenses such as marking untrusted content, separating planning from untrusted data, and checking actions against the user's original intent. Audit everything.
g-eval-what|Score agents on task success first, then on trajectory efficiency (steps, tokens, time), policy violations, correct abstention when the task is impossible, and cost and latency. A cheap agent that fails is worthless, and a successful agent that broke a policy may be worse than failure.
g-eval-how|Use deterministic graders (tests, state checks) wherever possible. Rubric-based LLM judges handle open-ended outputs. Keep held-out environments the agent was never tuned on. Run continuous evals on production samples. Control flakiness by fixing seeds, mocking unstable tools, and running multiple trials per task.
g-browser-ground|Browser agents act either through the DOM or accessibility tree (precise and cheap) or through screenshots with mouse and keyboard actions (general but slower). Define the action space: click, type, scroll, navigate. Prefer stable selectors over coordinates. Fall back to OCR for canvas or image-heavy pages. Combine visual and structural cues for robustness.
g-browser-safe|Browser agents meet hostile content constantly. Use domain allowlists. Keep credentials in a vault and inject them only into approved sites. Watch for phishing and malware downloads. Snapshot and reset browser state between tasks. Verify outcomes with independent checks, such as reading back a saved record, rather than trusting the agent's claim.
g-long-state|Long-horizon agents need durable state: workspace snapshots, diffs of what changed, and a subtask graph showing progress. Replay or time travel lets you inspect any past step. Give partial credit in evals so improvements in long tasks are measurable before full success.
g-long-ver|Verification keeps long runs on track. Tests act as graders. Plan-execute-verify (PEV) loops check each step. Critic agents review work. Human review points catch drift on high-stakes steps. Make rollback easy, for example via git, so a bad step can be undone cheaply.
g-train-trace|To train agents with RL in real harnesses, record exact token ids and logprobs from the sampler, not re-tokenized text. Use loss masks so the model learns only from its own tokens, not tool outputs. Account for harness rewrites such as compaction that alter context. Design rewards carefully and watch for hacking, such as gaming tests.
g-train-gen|Agents trained in one harness may not generalize. Train across several harnesses and diverse environments. Monitor entropy to avoid collapse into repetitive behavior. Distillation from a stronger agent is often cheaper than RL. Evaluate in held-out environments that mirror real use.
g-red-cases|Red-team agents across direct and indirect injection, tool abuse (using allowed tools for harmful ends), data exfiltration through outputs or links, privilege escalation via confused-deputy tricks, and malicious plugins or MCP servers.
g-red-ops|Track coverage across attack categories. Use a severity rubric so fixes are prioritized. Add regression cases to CI gates. Define bug bounty scope for agent features. Retest after every model, prompt or tool change, since defenses that worked last month may not work today.
g-org-levels|Autonomy is a dial: suggest only; draft and let a human send; act automatically within narrow scopes; supervised multi-agent work; and lights-out operation with audit. Move up only with evidence from evals and incident history.
g-org-risk|Risk operations for agents: kill switches that halt activity instantly; blast-radius limits on spend, records touched and messages sent; simulation before production; clear liability and insurance positions; and executive metrics that cover both value and incidents.
g-eco-std|Track standards that shape agent systems: MCP's evolution, A2A interop, skill and plugin packaging formats, agent evaluation standards, and gateway patterns. Adopt standards that reduce lock-in.
g-eco-mkt|The market includes host apps (IDEs, chat clients), managed agent platforms, vertical agents for specific industries, and growing compliance requirements. Ask which parts are commodities and where durable advantage lives: usually proprietary data, workflows and evals, not the model itself.
