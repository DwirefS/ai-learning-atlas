sc-math-la|Almost everything in a model is a vector or a matrix. An embedding is a list of numbers; a layer is a matrix that maps one list to another. The dot product of two vectors measures how aligned they are, which is why it shows up as "similarity" in attention and in vector search. SVD tells you how much of a matrix is really needed: if a few singular values dominate, a low-rank version is nearly as good, and that is exactly the bet LoRA makes. Broadcasting is the habit of thinking in whole tensors with batch, sequence and hidden dimensions rather than loops. Learn to read shapes like [batch, seq, d_model] and most papers become much easier.
sc-math-prob|A language model outputs a probability distribution over the next token. Training minimizes cross-entropy, the average surprise of the true token under the model, which is the same as maximum likelihood. KL divergence measures how far one distribution drifts from another; it is the leash in RLHF that keeps a tuned model near its reference. Entropy tells you how unsure the model is, which is useful for routing and abstention. Calibration asks whether "80% confident" is right 80% of the time, which is different from accuracy. Bayes is the mental tool for reasoning about evaluations: a 95%-accurate classifier on a 1% base-rate problem still produces mostly false alarms.
sc-math-opt|Training is gradient descent: compute how the loss changes with each weight (backprop is the chain rule applied efficiently) and nudge weights the other way. Adam keeps running averages of gradients and their squares so each weight gets its own step size; AdamW separates weight decay from that update, which matters for generalization. Learning-rate warmup avoids blowing up early when statistics are noisy, then cosine or linear decay settles the model. Gradient clipping caps rare huge updates. Watch both training and validation loss: if validation rises while training falls you are overfitting; if both stay high you are underfitting or the learning rate is wrong.
sc-nn-blocks|A neural network stacks simple layers: a linear map, a nonlinearity such as GELU or SiLU, and a loss at the end. Backprop sends error signals backward through every layer. Residual connections add the input of a block to its output, so gradients have a short path back and very deep networks stay trainable. Normalization (LayerNorm, RMSNorm) keeps activations in a sane range. Dropout and weight decay are regularizers that discourage memorization. Parameter counting is a practical skill: a transformer block has roughly 12·d² parameters (4·d² attention, 8·d² MLP), so you can sanity-check model sizes and memory before downloading anything.
sc-nn-rep|Networks learn representations: internal coordinates where similar things sit close together. That is why pretrained models transfer, since the features learned on a huge corpus are reusable for your task with little extra data. Scaling laws describe how loss falls smoothly as you add parameters, data and compute, and Chinchilla showed that many early models were undertrained for their size (roughly 20 tokens per parameter is compute-optimal). Inductive bias is what an architecture assumes before seeing data: convolutions assume locality, attention assumes little. Large over-parameterized models can still generalize well, which overturned the classic "more parameters means more overfitting" intuition.
sc-llm-tok|Models never see characters, only token ids. BPE and similar algorithms merge frequent byte pairs into a vocabulary of roughly 32k to 200k pieces. Fertility, the number of tokens per word, varies a lot by language and domain: code, Thai, or chemical names can cost several times more tokens than English prose, which hits both cost and context budget. Chat templates wrap messages with special tokens that mark roles; using the wrong template quietly degrades quality. Detokenization can split multi-byte characters across tokens, so streaming clients must buffer bytes. Always count tokens with the model's own tokenizer before you send.
sc-llm-attn|A transformer block is attention followed by a feed-forward network, each wrapped in a residual connection and normalization. Attention lets every token gather information from earlier tokens, weighted by query-key similarity. Multi-head attention runs several of these in parallel. GQA and MQA share key/value heads across query heads to shrink the KV cache; MLA compresses keys and values into a smaller latent. RoPE encodes position by rotating query and key vectors so relative distance shows up in their dot product. The causal mask stops tokens from peeking at the future, which is exactly what makes caching earlier keys and values valid during generation.
sc-llm-gen|Generation is a loop: run the model, get logits for the next token, pick one, append it, repeat. Greedy picks the top token; temperature reshapes the distribution (lower is sharper); top-k and top-p cut off the unlikely tail before sampling. Stop sequences end the loop. Constrained decoding masks tokens that would break a grammar or JSON schema, so output is valid by construction. Logprobs expose the model's confidence per token and are handy for classification and routing. Streaming sends tokens as they appear, which improves perceived latency but means your client must handle partial output and cancellation.
sc-long-ctx|A model may accept 1M tokens, but usable context is smaller: recall of facts buried in the middle often drops ("lost in the middle"), and cost and latency grow with length. KV cache memory grows linearly with tokens, and attention compute grows quadratically during prefill, so long prompts are expensive to serve. Sparse, sliding-window and chunked attention variants trade some quality for efficiency. RoPE scaling methods stretch positional encodings beyond training length. RAG still wins when the corpus is bigger than any window, changes often, or needs access control per document. Measure with needle-in-a-haystack and, better, task-level evals on your own long documents.
sc-mm|Vision-language models usually bolt a vision encoder onto an LLM: the image is cut into patches, encoded, projected into the token embedding space, and treated like extra tokens. A single high-resolution image can cost hundreds to thousands of tokens. For documents, classic OCR or PDF text extraction is often cheaper and more accurate than sending page images, with the VLM as a fallback for charts and layout. Speech systems pair speech-to-text and text-to-speech with an LLM, or use native audio models for lower latency. New modalities bring new attack surfaces, such as instructions hidden in images or audio.
sc-moe|Mixture-of-experts replaces the single feed-forward block with many experts and a small router that sends each token to the top-k of them (often 2 of 8, or 8 of 256). Only a fraction of the parameters run per token, so you get the quality of a big model at the compute of a smaller one. The catch is memory: all experts must be resident, so a 600B-parameter MoE still needs the HBM of a 600B model. Training adds load-balancing losses so experts are used evenly. Serving uses expert parallelism, which turns routing into all-to-all network traffic and makes batch composition matter.
sc-eval-what|Decide what "good" means before measuring. Capability (does it solve the task), safety (does it avoid harm and leaks), and cost/latency are separate axes and often trade off. For agents, outcome metrics (task done) and process metrics (steps, tool errors, policy violations) both matter. Offline evals on fixed sets catch regressions; online signals such as user edits, thumbs, and escalations catch what your set missed. Contamination happens when test items leaked into training data, inflating scores. Calibration and abstention matter in high-stakes domains: a model that says "I don't know" correctly is often worth more than one that is slightly more accurate.
sc-eval-how|Start with a golden set: 50 to 200 real, labeled examples with clear rubrics, built before you tune anything. LLM-as-judge scales grading but has biases (position, verbosity, self-preference), so calibrate it against human labels and keep the judge model and prompt versioned. Put evals in CI so prompt or model changes fail the build when quality drops. Shadow traffic and A/B tests validate changes on real users safely. Keep an error taxonomy (retrieval miss, hallucination, format error, refusal) so failures turn into specific fixes rather than vague "the model is worse" complaints.
sc-sec-threats|LLM systems mix instructions and data in one channel, so prompt injection is the signature threat: direct when a user types it, indirect when it hides in a web page, email, PDF or tool result the model reads. Poisoning plants bad behavior in training or retrieval data. The supply chain now includes model weights, tokenizers, plugins and MCP servers, any of which can be malicious. Secrets pasted into prompts end up in logs and traces. Attackers can also query a model to extract its behavior or test whether a record was in its training data. Treat every model output as untrusted input to the next system.
sc-sec-ctrl|You cannot reliably filter prompt injection, so design so it cannot do much damage. Give tools least privilege: narrow scopes, read before write, per-user credentials rather than a shared admin key. Run code and browsers in sandboxes with egress allowlists. Validate model output against schemas and business rules before acting on it. Put human approval in front of irreversible actions like sending money or email. Keep tamper-evident audit logs of prompts, tool calls and approvals so you can reconstruct incidents. Record provenance for models and data so you know exactly what was running when something went wrong.
a-sys-req|AI requirements need numbers on more axes than usual. Besides features, pin down latency (time to first token and total), quality (task success on an eval set), cost per request or per user per month, and availability. Ask where data may be processed and stored, and whether tenants must be isolated. Decide where humans review or approve. Write abuse cases alongside use cases: what happens when someone tries to jailbreak it, scrape it, or run up the bill? Requirements that skip these show up later as surprise invoices, compliance blockers, or a security incident.
a-sys-decomp|Break the system along boundaries that fail and scale differently. Keep the synchronous user path thin and push slow work (enrichment, indexing, long agent runs) to async queues. Separate failure domains so a model provider outage degrades one feature instead of the whole product. Use strangler patterns to replace legacy flows incrementally rather than in a big bang. Design degraded modes up front: cached answers, a smaller fallback model, or a "we're busy, here's a form" path. A good decomposition makes it obvious which team owns which latency and cost budget.
a-mlsys-pipe|An AI system is a pipeline, not a model: data flows into adaptation (prompts, RAG indexes, fine-tunes), into evaluation, into serving, and into monitoring that feeds back into data. Offline signals (eval scores) and online signals (user behavior) must both exist. Release with shadow, canary or blue-green deployments, exactly as with code. Track lineage so every response can be traced to a prompt version, model version, index snapshot and config. Without lineage you cannot answer the most common incident question: what changed?
a-mlsys-debt|AI systems accumulate unusual debt. Data drift shifts inputs; concept drift changes what the right answer is. Prompts and configs drift as people tweak them in production without review. Harness drift happens when the agent framework changes behavior underneath you. Glue code between models, retrievers and tools grows into a jungle with no tests. The fix is boring discipline: version prompts and configs like code, monitor input distributions, assign an owner to every metric, and schedule regular eval refreshes so the golden set still reflects real traffic.
a-llm-types|Know the categories. Frontier APIs give top capability with no ops burden but less control over data, versions and cost. Open-weight dense models can be self-hosted and tuned, at the cost of running GPUs. MoE models give big-model quality with smaller compute per token but large memory footprints. Small language models run cheaply on CPUs, phones and edge boxes for narrow tasks. Vision-language and speech models add modalities with their own latency and cost profiles. Most real architectures mix several of these behind one gateway.
a-llm-select|Leaderboards are a starting filter, not an answer: benchmarks leak into training data and rarely match your domain. Read licenses carefully, since "open weights" may still restrict commercial use or user counts. Tokenizer and chat template choices create quiet lock-in in prompts and fine-tunes. Check tool-calling and structured output maturity if you are building agents. The only reliable selection method is running two or three candidates on your own golden set and comparing quality, latency and cost per successful task.
a-ref-pat|A handful of patterns cover most AI products. An LLM API facade wraps providers behind your own interface. RAG with citations grounds answers in your documents. Batch enrichment runs models over large datasets offline for classification or extraction. Agent workers execute multi-step tasks from a queue with tools and budgets. Human review queues route low-confidence or high-risk outputs to people. Knowing these lets you sketch a credible architecture in a first client meeting and then adjust for their constraints.
a-ref-layers|Draw AI systems in layers: edge (auth, rate limits), API, orchestration (prompts, agents, workflows), model (gateway, serving), and data (indexes, stores). Separate the control plane, where policies, routing rules, prompt versions and budgets live, from the data plane that handles requests. Plan multi-region failover for both models and indexes. Shared services such as identity, billing, observability and secrets should be reused, not rebuilt per feature. Clear layers make it easy to swap a model or vendor without rewriting the product.
a-bb-dim|Compare options on five axes. Capability ceiling: can anything but a frontier model do the task? Latency and region: where must inference run? Sovereignty: can data or weights leave the boundary? Unit economics: what is the cost per successful task at expected volume? Lock-in and exit: how hard is it to switch providers? Score each option against these explicitly with the client so the decision survives a change of leadership or a price change.
a-bb-opt|The realistic menu is: frontier APIs, cloud-managed platforms (Bedrock, Vertex, Azure AI Foundry), self-hosted open weights on your GPUs, or a hybrid with routing. Hybrid is common: cheap or private traffic goes to a self-hosted model, hard queries go to a frontier API. A gateway layer (LiteLLM, Envoy AI Gateway, Kong, or a cloud gateway) gives one API, keys, budgets and fallbacks across all of them. Self-hosting only pays off above a utilization threshold, so do the math first.
a-data-plat|AI rides on the data platform. A lakehouse or warehouse holds governed source data. Retrieval needs both vector and keyword indexes, ideally fed from the same pipeline. A catalog with lineage and quality checks tells you where each chunk came from and whether it is fresh. Embedding stores must be versioned with the embedding model, because changing models means re-embedding everything. Think about access patterns early: per-user ACL filtering at query time is far easier if permissions are stored as chunk metadata from day one.
a-data-gov|Before data feeds a model, know whether you have the right to use it for that purpose, especially for training. Scan for PII, PHI and secrets before indexing. Set freshness SLAs so stale documents do not produce confident wrong answers. Standardize chunking and metadata (source, owner, ACL, timestamp) across teams. Plan deletion end to end: removing a source document must also remove its chunks, embeddings, cache entries and any derived summaries, or you will fail a right-to-erasure request.
a-gw-feat|A model gateway sits between apps and model providers. It normalizes APIs so apps call one interface, holds provider keys so apps never see them, and enforces per-team budgets and rate limits. It adds fallbacks (switch provider on errors) and hedging (send a second request if the first is slow). Policy hooks run PII redaction, prompt-injection screening or content filters on the way in and out. Every call emits a unified trace with tokens, cost and latency, which makes it the natural place to measure and govern AI usage.
a-gw-cache|A semantic cache returns a stored answer when a new prompt is close enough in embedding space to an old one. It can cut cost and latency sharply for FAQ-like traffic. The risks are wrong hits and leaks: the similarity threshold must be tuned on real pairs, keys must include tenant, model and prompt version, and TTLs must respect how fast the truth changes. Never share cache entries across tenants or permission levels. Provide bypass rules for personalized, time-sensitive or tool-using requests.
a-sec-tm|Start by listing assets: model weights, system prompts, training and retrieval data, tool credentials, user data. Then trace how untrusted text reaches the model, including indirect paths through documents, web pages, emails and tool outputs. The confused deputy is the key agent risk: the agent has permissions the attacker lacks and can be talked into using them. Add supply chain (models, packages, MCP servers) and abuse at scale (scraping, cost attacks). STRIDE still works; extend it with MITRE ATLAS and the OWASP LLM Top 10.
a-sec-ctrl|Controls that work regardless of model behavior: put tools and code execution in network-isolated sandboxes; use allowlists and human approvals for sensitive actions; keep secrets in a vault and inject short-lived, scoped tokens per call; log every prompt, tool call and approval in immutable storage; and schedule red-team exercises on a cadence, not once. Prefer architectural limits (the agent literally cannot reach the payments API) over prompt instructions (please don't touch payments).
a-gov-fw|The EU AI Act sorts systems into risk tiers, with heavy obligations for high-risk uses and transparency duties for general-purpose models. NIST AI RMF gives a voluntary govern-map-measure-manage structure widely used in the US. ISO/IEC 42001 is a certifiable AI management system standard, similar in spirit to ISO 27001. Sector rules (HIPAA, financial model risk guidance such as SR 11-7, and others) still apply. Contracts flow obligations down to vendors, so your model provider's terms become part of your compliance story.
a-gov-ops|Governance becomes real through artifacts and roles. Model and system cards document purpose, data, evals and limitations. AI impact assessments (often alongside DPIAs) record risks and mitigations before launch. Name who provides human oversight and what they can override. Extend incident response to cover AI failures such as harmful outputs, data leaks, or agent misbehavior. Keep evidence (eval results, approvals, change logs) organized so an auditor can follow it without a week of archaeology.
a-cost-units|Learn to compute cost per request: input tokens times input price plus output tokens times output price, with output typically 3 to 5 times more expensive. Prompt or prefix caching discounts repeated input heavily. For self-hosting, convert GPU-hour cost and measured throughput into dollars per million tokens. Do not forget egress, storage for logs and indexes, eval runs, and human review time, which can exceed model spend. The useful metric is cost per successful task, not cost per call.
a-cost-ctrl|Cost control is mostly architecture. Set per-tenant and per-feature budgets enforced at the gateway. Route easy queries to small models and escalate only when needed. Move anything that is not interactive to batch APIs, often half price. Show teams their spend (showback) or charge it back so incentives line up. Alert on anomalies such as a sudden jump in tokens per request, which usually means a prompt bug, a loop, or abuse.
a-priv-min|The cheapest data to protect is data you never send. Strip or mask identifiers before prompts leave your boundary. Redact logs and traces by default. Apply field-level controls so the model sees only fields needed for the task. Review vendor data processing agreements for retention, training use and subprocessors, and turn off training-on-your-data where offered. Minimization reduces breach impact, regulatory scope and vendor risk all at once.
a-priv-ops|Privacy is an ongoing operation. Set retention schedules for prompts, outputs and traces. When a user or document is deleted, purge it from indexes, caches and memories too. Review who can read raw logs and traces. Have a breach playbook that covers AI-specific leaks such as a model repeating another user's data. Respect data residency by pinning processing regions, including for embeddings and evals, not just the main model call.
a-scale-ten|Multi-tenant AI systems need isolation in places classic SaaS does not. One heavy tenant can saturate shared GPUs, so use quotas, fair queuing and priority classes. Give each tenant its own keys, budgets and rate limits. Partition data so retrieval filters by tenant at the index level, not in the prompt. Watch for cross-tenant leakage through shared semantic caches, shared memories or fine-tunes trained on mixed data.
a-scale-ha|Set RPO and RTO for every stateful part: model artifacts, vector indexes, prompt registries, conversation state. Replicate artifacts across regions ahead of time, since pulling 100+ GB of weights during an outage is slow. Use the gateway to shift traffic between regions and providers. Define degraded modes and practice failover in game days. A secondary provider with a different model also needs prompt and eval compatibility, or failover will quietly drop quality.
a-plat-cap|An internal AI platform bundles the things every team would otherwise rebuild: a gateway with routing and budgets, a prompt and configuration registry with versions, a shared evaluation service, a sandboxed tool runtime for agents, and cost dashboards. The goal is that a product team can ship a safe, observable AI feature in days without becoming experts in GPUs or security.
a-plat-dx|Platforms succeed through developer experience. Offer golden paths: templates that come with auth, tracing, evals and guardrails already wired. Make safe defaults the easy path. Turn on observability automatically. Make costs visible per team. Prefer self-service with policy guardrails over ticket queues, because teams route around slow platforms and that is how shadow AI starts.
a-cards-doc|Documentation is how trust scales. Model cards describe what a model is, how it was trained and evaluated, and where it fails. System cards describe the whole application, including prompts, tools, guardrails and human oversight. Publish eval summaries and known limitations honestly. Keep a change log of model and prompt versions so users and auditors can match behavior to releases.
a-cards-buy|Procurement for AI has new details. API terms of service and open-weight licenses differ: check commercial use, user thresholds, and output ownership. List subprocessors and data locations. Prepare for security questionnaires that ask about training on customer data, retention, and isolation. Negotiate exit terms, including data return and deletion. Ask about indemnity for IP claims on outputs, and check whether your insurance covers AI-related incidents.
a-sov-ctrl|Sovereign and regulated deployments keep weights, prompts, logs and embeddings inside a legal and physical boundary. Confidential computing and GPU TEEs protect data in use from the cloud operator. Evals and red-teaming run inside the boundary too. Models arrive through a signed supply chain with verified hashes. Embedding and search run locally so documents never leave. A private network link to a public model API does not satisfy these requirements on its own.
a-sov-ops|Operating inside a boundary changes daily work. Updates arrive as signed bundles, sometimes physically carried in. Break-glass access for emergencies is logged and time-limited. Telemetry must be designed so metrics leave but data does not. Auditors expect evidence packs. Field support may require cleared staff on site, so the support model is part of the architecture, not an afterthought.
a-org-model|Organizations typically pick a Center of Excellence (central experts), a federated model (each business unit builds), or hub-and-spoke (central platform plus embedded builders). Separate the platform team, which provides paved roads, from product teams, which ship features. Write a RACI for AI incidents. Keep a skills matrix so you know who can do evals, infra, security and domain review. Manage vendors centrally to avoid twenty contracts with the same provider.
a-org-change|Pilots are easy; scaling is hard. Define criteria to graduate a pilot: measured quality, cost per task, security review, owner on call. Watch for shadow AI, where teams use unapproved tools because the official path is slow. Control sprawl by consolidating gateways and prompt stores. Report executive metrics in business terms such as hours saved or resolution rate, and invest in training so staff know what the tools can and cannot do.
