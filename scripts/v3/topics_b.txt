e-api-client|A solid LLM client handles the boring failures. Know the API shapes: chat completions, newer responses-style APIs with built-in tools and state, and legacy completions. Streaming uses server-sent events; parse incrementally and handle disconnects. Retry 429 and 5xx with exponential backoff and jitter, and use idempotency keys when the call triggers side effects. Set connect and total timeouts and propagate user cancellation so you stop paying for tokens nobody will read. Log input, output and cached token counts on every call so cost is measurable per feature.
e-api-msg|Messages carry roles (system, user, assistant, tool) that the provider turns into a chat template. Put durable instructions in the system message and task data in user turns. Few-shot examples help most for format and edge cases; keep them short and representative. Budget context explicitly: instructions, retrieved data, history and room for the answer must fit. For multi-turn apps, decide what state you keep server-side versus resend each turn. Providers differ in tool-call formats, max output limits and how they treat system prompts, so wrap them in an adapter.
e-prompt-tech|Clear prompts state the task, the audience, constraints and the output format, and include an example when format matters. Chain-of-thought helps on multi-step reasoning but costs tokens; reasoning models do it internally, so explicit CoT prompts matter less there. Self-consistency samples several answers and takes the majority, trading cost for accuracy. Use JSON schema or structured output modes instead of begging for JSON. Wrap untrusted content in clear delimiters and tell the model it is data, which helps but does not stop determined injection.
e-prompt-ctx|Context engineering means choosing what goes into the window and in what order. Sources include the system prompt, retrieved documents, memory, tool results and conversation history. Models attend best to the start and end, so put key instructions and the most relevant evidence there. When history grows, compact it by summarizing older turns while pinning facts that must survive. Require citations to retrieved chunks so answers can be verified. Most quality problems in production apps are context problems, not model problems.
e-tok-bpe|Token counts drive cost, latency and truncation. Measure fertility on your real data: JSON, code, logs and non-English text often tokenize poorly. Special tokens such as end-of-turn markers must never appear in user content unescaped. When text is too long, choose a truncation strategy deliberately (keep the head and tail, summarize the middle, or retrieve) instead of chopping silently. Count tokens with the provider's tokenizer before sending so you can reject or compact oversized requests early.
e-emb|Embeddings turn text into vectors for search. Bi-encoders embed queries and documents separately, which is fast and indexable; cross-encoders read the pair together and are more accurate, so use them to rerank a shortlist. Matryoshka (MRL) models let you truncate vectors to fewer dimensions with modest quality loss, saving memory. Cosine similarity is standard; normalize vectors so dot product equals cosine. Some models use different prefixes or encoders for queries and documents. Re-evaluate when your domain drifts, and remember that changing embedding models means re-indexing.
e-tools-des|Design tools around tasks the model needs, not around your database tables: "refund_order(order_id, reason)" beats generic CRUD. Descriptions are prompts, so write them for the model, with when-to-use guidance and examples. Use strict argument schemas with enums and required fields. Classify side effects as read, reversible write or irreversible write, and make writes idempotent with keys so retries do not double-charge. Return compact, structured results and clear error messages the model can act on.
e-tools-loop|The tool loop is: model proposes calls, harness executes, results go back, repeat until the model answers. Run independent calls in parallel. When a tool fails, return a useful error so the model can repair arguments on the next turn rather than crashing. Cap iterations and total tokens so loops cannot run forever. Insert human confirmation before irreversible actions. Give each tool its own timeout so one slow API does not stall the whole run.
e-rag-index|Indexing quality sets the ceiling for RAG. Chunk on structure (headings, sections) rather than fixed character counts, with modest overlap. Pick embeddings by testing retrieval on your data. Attach metadata (source, date, ACL, section) to every chunk so you can filter and cite. Combine BM25 keyword search with dense vectors, since each catches what the other misses. For complex corpora, hierarchical or graph indexes capture relationships that flat chunks lose.
e-rag-query|At query time, rewrite vague or conversational questions into standalone searches; HyDE generates a hypothetical answer and searches with it. Multi-hop questions need iterative retrieval where each step informs the next. Retrieve broadly (say 50 candidates) then rerank with a cross-encoder down to the best 5 to 10. Force the model to cite chunk ids and to say when the evidence does not cover the question. Good refusals are a feature, not a failure.
e-rag-fail|RAG fails in recognizable ways. The answer was split across two chunks and neither alone is enough. The index is stale. A document contains injected instructions that the model follows. Too many weak chunks drown the relevant one. Evals only test easy questions so problems stay hidden. Diagnose by logging retrieved chunks with every answer and labeling failures as retrieval misses versus generation errors; the fixes are completely different.
e-cache-des|Semantic caching stores responses keyed by prompt embeddings and returns a hit when a new prompt is similar enough. The similarity threshold is the main knob: too low and users get wrong answers, too high and nothing hits. Build keys from the embedding plus tenant, model, prompt version and relevant parameters. Use TTLs and event-based invalidation when source data changes. Bypass the cache for personalized or tool-using requests. Expect a cold start with no hits until traffic builds the cache.
e-cache-ops|Track hit rate, false-hit rate (sampled and reviewed), latency saved and dollars saved. A poisoned cache, where one bad answer gets served thousands of times, is the classic incident, so keep a way to purge by key pattern instantly. Put the policy version in the key so changes invalidate old entries automatically. In multi-region deployments decide whether caches are regional or replicated. Attribute savings to teams so the value is visible.
e-eval-suite|A product eval suite covers capability (does it solve tasks), safety (refusals, leaks, harmful content) and style (tone, format). Mix golden examples from real traffic with adversarial cases. For agents, add process metrics such as steps taken and tool errors. Track cost and latency per case alongside quality so trade-offs are explicit. Slice results by user cohort, language and task type, because averages hide the segment that is failing.
e-eval-ops|Treat evals as code. Version prompts, models and judge configs together so results are reproducible. Calibrate LLM judges against human labels periodically. Sample production traffic into review queues to find new failure types and feed them back into the golden set. Show regression dashboards per release. Quarantine flaky cases and fix their nondeterminism rather than ignoring red results.
e-agents-when|Most problems that look like agent problems are workflows: a fixed sequence of steps with an LLM inside some of them. Workflows are cheaper, faster and easier to test. Model the task as a state machine first. Use a single tool-using agent when steps genuinely depend on intermediate results. Only reach for multiple agents when tasks are parallel or need very different contexts. Always define human escalation and step, token and dollar budgets.
e-agents-impl|A practical agent runs plan, act, observe in a loop. A scratchpad or todo list keeps the plan visible across turns. Subagents can handle isolated subtasks with fresh context and return summaries. Wrap fragile operations in deterministic code rather than asking the model to do them. Make every side-effecting tool idempotent so a retry after a crash does not repeat work. Log the full trajectory for debugging and evals.
e-prod-rel|Production LLM features need the reliability patterns of any distributed system. Set timeouts and circuit breakers on model calls. Configure fallback models or providers. Put async work on queues with backpressure so spikes do not cascade. Make writes idempotent. Shed low-priority load when capacity is short. Test these paths deliberately, because a provider outage is a matter of when, not if.
e-prod-obs|Trace every request across retrieval, model calls and tools with structured spans (OpenTelemetry GenAI conventions help). Record tokens, cost, latency and model version per span. Sample outputs for quality review. Alert on drift in quality scores, refusal rates or tokens per request, not only on errors. Redact secrets and personal data before traces are stored, since traces are a common source of leaks.
e-prod-sec|Authorize every tool call against the end user's permissions, not the app's service account. Filter outputs for sensitive data and unsafe content before display or action. Redact PII before sending to third-party models where possible. Pin dependency and model versions to avoid supply-chain surprises. Enforce spend caps per user and per key so an abuser or a runaway loop cannot generate a five-figure bill overnight.
e-ft-when|Fine-tune only after prompts and retrieval hit a ceiling you can measure. Fine-tuning is good at style, format, narrow skills and making smaller models act like bigger ones; it is bad at teaching fresh facts, which RAG handles better. You need clean, representative data, usually hundreds to thousands of examples. Watch for catastrophic forgetting of general skills. Check that the base model's license allows tuning and your use.
e-ft-how|Supervised fine-tuning (SFT) trains on input-output pairs. LoRA freezes the base model and learns small low-rank matrices, cutting memory and producing swappable adapters; QLoRA does this on a 4-bit base. Preference methods such as DPO, ORPO and KTO learn from chosen-versus-rejected pairs without a separate reward model. Synthetic data can bootstrap training but must be filtered and validated. Always compare the tuned model to the base on your eval suite before merging.
e-ft-ops|Version datasets alongside checkpoints. Pick checkpoints by eval score, not by the lowest training loss. Run regression suites that include general capabilities, not just the target task. Keep the previous adapter ready for instant rollback. Budget for refreshes: when the base model gets a new release, you may need to retrain, so automate the pipeline.
e-synth-gen|Synthetic data comes from prompting a strong teacher model to produce examples. Control diversity with varied seeds, personas and topics, or you get thousands of near-duplicates. Filter with critique loops, verifiers, or executable checks such as unit tests. On-policy traces from your own model capture its real mistakes. Check that synthetic items do not overlap your evaluation set, or scores become meaningless.
e-synth-dist|Distillation trains a smaller student to imitate a larger teacher. Logit distillation matches the teacher's full output distribution, which carries more signal than single answers; response distillation trains on teacher outputs only and works with API teachers. Task-specific students can be ten times cheaper with similar quality on that task. Students inherit teacher errors and biases. Plan a refresh cadence as teachers improve.
e-multi-route|Routing sends each request to the cheapest model likely to handle it. Heuristic routers use rules (length, keywords, user tier); learned routers predict difficulty from features. Confidence signals such as logprob entropy or a verifier score can trigger escalation. Cascades try a small model first and defer to a larger one when unsure. Run A/B assignment to measure the quality and cost effect of every routing change.
e-multi-ens|Ensembles spend more compute for quality. Best-of-N samples several answers and picks the best with a scorer. Verifier models check answers, which works especially well when correctness is checkable (code, math). Debate and critique loops have models review each other. Cap cost per request and keep latency inside the SLO, because ensembles multiply both quickly.
e-fly-cap|A data flywheel turns usage into improvement. Capture traces only with consent and redaction in place. Mine failures from explicit feedback, user edits, retries and escalations. Use active learning to queue the most informative examples for labeling. Watch sampling bias: users who give feedback are not representative, and you will over-fit to them if you are careless.
e-fly-use|Captured data feeds several loops: new eval cases, SFT examples, preference pairs from edited or rejected answers, reward signals for RL, and regression tests for prompts. Publish a regular quality report that shows how the flywheel moved key metrics. A flywheel that only collects data without changing the product is just storage cost.
e-edge-stack|Edge apps run quantized models (GGUF via llama.cpp, MLX, ONNX Runtime, Core ML, or vendor NPU runtimes) on CPUs, GPUs or NPUs. Memory is the binding constraint: a 7B model at 4-bit is about 4 GB, before KV cache. Hybrid designs keep simple or private tasks local and send hard ones to the cloud. Plan model update channels with signatures and delta downloads, since models are large.
e-edge-ux|On-device AI has UX costs. The first load of a model can take seconds. Offline mode should degrade gracefully rather than fail. Tell users plainly what stays on device and what goes to the cloud. Provide degraded modes on low battery or thermal throttling. Measure battery impact; a feature that drains the phone gets uninstalled.
e-post-map|Post-training turns a base model into an assistant. SFT teaches format and behavior from demonstrations. Preference learning, via RLHF with a reward model or RLAIF with AI feedback, teaches which answers people prefer. DPO, ORPO and KTO do preference learning directly from pairs without the RL loop. GRPO and environment-based RL reward verifiable success, such as passing tests. Distillation copies a stronger model's behavior, often cheaper than RL for narrow goals.
e-post-risk|Training can make things worse. Models over-fit to the harness or eval used in training. Reward hacking finds loopholes, such as editing tests instead of fixing code. Entropy collapse makes outputs repetitive and kills exploration. Contaminated evals hide all of this. Often the right call is not to train at all and instead improve prompts, retrieval or tools.
e-mm-pipe|Multimodal pipelines should use the cheapest reliable path first: extract text from PDFs and run OCR, and send page images to a VLM only for charts, handwriting or layout-heavy pages. Speech goes through STT before an LLM unless latency demands a native audio model. Screenshots power UI understanding and computer-use agents. Gate inputs by size and MIME type to control cost and attack surface.
e-mm-eval|Each modality needs its own gold data: scanned forms, charts, accents, noisy audio. Test adversarial images, including text hidden in pixels that tries to inject instructions. Scan uploaded files for malware before processing. Accessibility matters too: generated alt text and transcripts should be checked for accuracy, since users may rely on them.
i-life-stages|An inference request passes through clear stages. The server applies the chat template and tokenizes. Prefill processes the whole prompt in parallel; it is compute-bound and sets time to first token. Decode generates one token per step for every sequence in the batch; it is memory-bandwidth-bound because each step re-reads all weights and the KV cache. Detokenization and tool-call parsing turn ids back into text and structure. Streaming returns tokens as they come; buffering waits for the full output.
i-life-metrics|TTFT (time to first token) measures prefill plus queueing. TBT or ITL (time between tokens) measures decode speed per user. Throughput is tokens per second per GPU across all users. Goodput counts only requests that met their SLOs, which is what actually matters. KV cache hit rate shows how much prefix reuse you get. Queue time reveals under-provisioning before latency explodes. Always report percentiles (p50, p95, p99), not averages.
i-eng-open|vLLM popularized PagedAttention and continuous batching and supports most models and hardware. SGLang adds RadixAttention for automatic prefix reuse and is strong for structured and agentic workloads. TGI is Hugging Face's server. llama.cpp and Ollama run quantized models on CPUs, Macs and small GPUs. Compare on features you need (quantization formats, speculative decoding, LoRA, structured output, disaggregation) and benchmark on your own traffic shape.
i-eng-nv|TensorRT-LLM compiles models into optimized engines for NVIDIA GPUs, often the fastest option at the cost of build steps. Triton Inference Server hosts many model types behind one API. NVIDIA Dynamo orchestrates distributed and disaggregated serving with KV-aware routing. NIM packages models as ready-to-run containers. Migrating between stacks costs engineering time, so weigh peak speed against operability.
i-mem-fit|GPU memory holds weights, KV cache and activations. Weights are parameters times bytes per parameter: 70B at FP16 is 140 GB. KV per token is 2 × layers × KV heads × head dim × bytes. Activation peaks happen in prefill of long prompts. Fragmentation wastes memory unless the engine pages it. Engines reserve a fraction of memory up front (for example gpu_memory_utilization 0.9), so nvidia-smi shows "full" even when idle.
i-mem-tech|PagedAttention stores KV in fixed blocks like virtual memory pages, so there is almost no fragmentation and sequences can share prefix blocks. Quantizing KV to FP8 halves its size. Offloading cold KV to CPU memory or NVMe extends effective capacity at a latency cost. Prefix sharing lets requests with the same system prompt reuse KV. Capping max sequence length per tier is a simple and effective policy for protecting memory.
i-batch-types|Static batching waits for a full batch and holds GPUs until the longest sequence finishes. Continuous batching adds and removes sequences every step, keeping the GPU busy. Chunked prefill splits long prompts into pieces mixed with decode steps so a big prompt does not freeze everyone's token stream. Schedulers can preempt low-priority requests and enforce fairness between tenants. Knobs such as max batched tokens and max sequences trade latency against throughput.
i-kv|The KV cache stores keys and values for past tokens so decode does not recompute them. Paged blocks manage it efficiently. Prefix caching reuses KV for identical prompt prefixes across requests; RadixAttention organizes cached prefixes as a tree for automatic matching. When memory fills, the engine evicts least-recently-used blocks or preempts sequences. FP8 or INT8 KV roughly doubles capacity with small quality cost on most models.
i-quant-w|Weight quantization stores weights in fewer bits. GPTQ and AWQ produce INT4 weights with small accuracy loss using a calibration set; GGUF is llama.cpp's format with many variants. FP8 on Hopper and newer GPUs keeps quality very close to BF16 with hardware support. Calibrate on data like your traffic. Per-channel or group scales handle outlier columns. Always re-run your evals after quantizing, because averages can hide broken edge cases.
i-quant-kv|Activations and KV are harder to quantize than weights because of outliers, a few huge values in certain channels. SmoothQuant shifts that difficulty from activations into weights. KV FP8 is widely supported and usually safe. Symptoms of quantization collapse include repetition, broken formatting and wrong math. Mixed schemes keep sensitive layers in higher precision while quantizing the rest.
i-spec-m|Speculative decoding guesses several tokens cheaply and verifies them in one pass of the big model. A small draft model can propose tokens. EAGLE and Medusa add lightweight heads to the target model. N-gram lookup copies spans from the prompt, great for editing and RAG. Multi-token prediction (MTP) trains the model to predict ahead. Tree verification checks several candidate branches at once. Output distribution stays the same as the target model when done correctly.
i-spec-lim|Speedup depends on acceptance rate: how often the target agrees with the draft. Predictable text (code, templated output) accepts well; creative text less so. At large batch sizes the GPU is already busy, so verification overhead can erase the gain. The draft model costs memory and compute too. Benchmark at your real concurrency and tune the number of speculated tokens.
i-struct-tech|Constrained decoding compiles a JSON schema or grammar into a state machine and masks invalid tokens at each step, so output always parses. Token healing fixes boundary issues where the prompt ends mid-token. Partial JSON repair helps clients that parse streams. Tool-call parsers extract function calls from model-specific formats. Version schemas, since changing a schema can change model behavior.
i-struct-ops|Grammar compilation costs time, so cache compiled schemas. Constraints can interact with prefix caching and speculative decoding in engine-specific ways. Failure modes include the model being forced into valid but wrong values, or long loops of whitespace. Agree on contracts with clients about required fields and error handling. Monitor schema violation and repair rates.
i-pd-why|Prefill is compute-heavy and bursty; decode is memory-bound and steady. On shared GPUs, a large prefill stalls ongoing decodes (interference), hurting time between tokens. Disaggregation runs them on separate GPU pools sized for each phase, so you can match the prefill-to-decode ratio to your input and output lengths. It wins for long inputs and strict latency SLOs; for short prompts and small deployments, co-location is simpler and cheaper.
i-pd-impl|In a disaggregated setup, a router sends a request to a prefill worker, which computes the KV cache and transfers it to a decode worker over NVLink or RDMA (NIXL, Mooncake and similar libraries do this). The proxy coordinates handoff and streaming. Capacity planning sets the ratio of prefill to decode GPUs. New failure modes include stuck KV transfers and imbalance between pools, so monitor transfer latency and queue depth on both sides.
i-dist-types|When a model does not fit on one GPU, split it. Tensor parallelism splits each layer's matrices across GPUs and needs fast all-reduce, so keep it within an NVLink domain. Pipeline parallelism assigns layers to stages, tolerating slower links but adding bubbles. Expert parallelism places MoE experts on different GPUs with all-to-all routing. Sequence or context parallelism splits very long sequences. Large deployments combine them.
i-dist-comm|Distributed inference lives or dies on communication. NCCL provides collectives such as all-reduce and all-to-all. NVLink and NVSwitch give hundreds of GB/s inside a node or rack; InfiniBand or RoCE connect nodes at lower bandwidth. Good engines overlap communication with compute. Place tensor-parallel groups inside the fastest domain and check the topology with nvidia-smi topo -m before blaming the model.
i-lora-mem|Multi-LoRA serving keeps one base model in memory and loads many small adapters. Adapters are megabytes to hundreds of megabytes each. The router sends each request to a server that has its adapter loaded; hot adapters stay in GPU memory, cold ones live in CPU or disk. Kernels such as Punica and S-LoRA batch requests with different adapters together. Quantized adapters save more memory.
i-lora-ops|Treat adapters as deployable artifacts with versions. Canary new adapters on a slice of traffic. A heavily used adapter can starve others, so enforce fairness. Keep rollback instant by retaining the previous version. Emit metrics per adapter (latency, errors, quality) so tenant-specific problems are visible.
i-kern-attn|FlashAttention computes attention in tiles that stay in fast on-chip SRAM, avoiding writing the huge score matrix to HBM; it is exact, just IO-aware. GQA and MQA kernels exploit shared KV heads. Paged attention kernels read KV from scattered blocks. MLA variants decompress latent KV on the fly. Numeric modes (BF16, FP8) change speed and accuracy, and newer GPUs add special instructions for them.
i-kern-tool|Profile before optimizing. Nsight Systems shows the timeline of kernels, copies and gaps; Nsight Compute digs into one kernel. Triton lets you write custom GPU kernels in Python. CUDA graphs remove CPU launch overhead, which matters a lot in decode. torch.compile fuses operations automatically. The roofline model tells you whether a kernel is limited by compute or memory bandwidth, and therefore which optimization can help.
i-slo-plan|Capacity planning starts with load shape: requests per second, input and output lengths, and how bursty traffic is. Concurrency is not batch size; many concurrent users can be served by continuous batching on few GPUs until KV memory runs out. Autoscale on queue depth or tokens in flight, not CPU. Keep warm pools because cold starts on GPUs take minutes. Hold headroom for spikes and failures.
i-slo-deg|When demand exceeds capacity, degrade on purpose. Admission control rejects or queues requests before they hurt everyone. Shed non-critical traffic such as batch jobs first. Fall back to a smaller model for some tiers. Use priority lanes so paying or interactive users keep their SLOs. Communicate clearly during incidents, including status pages, because silent slowness erodes trust faster than an honest message.
i-hw-plat|Hardware sets serving economics. NVIDIA Blackwell and GB200 NVL72 racks connect 72 GPUs in one NVLink domain, ideal for big MoE models. AMD Instinct GPUs with ROCm offer large HBM and are supported by major engines. CPU-plus-GPU superchips share memory coherently. Other accelerators (TPUs, Trainium, Gaudi, inference ASICs) can be cheaper for supported models. Power per rack is now a first-class constraint.
i-hw-mem|HBM capacity decides how many sequences and how much context fit; HBM bandwidth decides decode speed. KV offload to CPU or NVMe and CXL memory pools extend capacity. Multi-host KV stores let any server reuse cached prefixes. Each extra tier adds latency and new failure domains, so measure hit rates before adding complexity.
i-res-topics|Inference research moves monthly. Watch better speculation methods, learned schedulers that predict output length, cross-request KV sharing at cluster scale, energy-aware serving that trades a little latency for power, smarter MoE expert placement, and new variants of disaggregation. Before adopting a paper, check whether the gains hold at your batch sizes, models and hardware, and whether a maintained engine already implements it.
